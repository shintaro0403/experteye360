## 4. ユーザーと合意した方針

### 4.1 開発の進め方

- **まず計画を盤石にし、AI で爆速** — OK。正本（TEST-DESIGN §1.2、DOC-ALIGNMENT）を渡し、**中粒度 1 ファイルずつ** `npm test` Green がよい
- **TDD プロジェクトと言えるか** — **方針・計画としては Yes**。**実践が回っている成熟フェーズでは No**（Phase 0 序盤）

### 4.2 テスト仕様の追加案

**正常・異常の列挙**

- **採用（明文化）** — 既に TEST-DESIGN §2.2 に近い内容あり。TC 表に「正常・境界・異常」列テンプレを足す程度で十分

**失敗テストを `failedTest.md` に残す**

- **常設ファイルは非推奨** — すぐ古れる・Vitest 出力と二重・AI が誤読しやすい
- **代替** — `npm test` / CI を正本。調査は短命メモ（`AI-history/`）または Issue。未決定は `it.skip` + 理由

### 4.3 README と docs の差異修正（ユーザー指示）

**A1** — PDF は **未実装**（§6 に明記）

**A2** — **比較機能なし**（README から「比較」表現を削除）

**A3 / A4** — **docs・コードに合わせる**（`localStorage`、平文照合、`npm test`、別オリジン非共有）

**B1** — ベテラン**テンプレ不採用**（「テンプレ」表記をカード設定等に修正）

**B2** — **別の回答は不要・削除**（SPEC・INVENTORY・`ParticipantPage`）

**B3** — **並び・フィルタ UI なし**

**B4 / C2** — 判断基準は **プロダクトも単一選択のみ**（D-10 決定）

**C1** — §6 を **「講師・管理者向け画面」** と平易に。F7 は開発用 ID と注記

**C3** — D-16: **ルート Vitest 1 本**（`vitest.config.ts` + `npm test`）

**C4** — 実装状況を **一元化**（DOC-ALIGNMENT §2 正本、README は抜粋）

**D1 / D3** — INVENTORY §8・§9、未来ファイル名参照は **そのまま**

**D2** — TECHNICAL-SPEC §4.3.12 修正

**D4** — README に local 平文 vs 本番 hash の違いを記載

### 4.4 記載形式（縦ブロック）

- **ファイル内の横並び表（`| … |`）は禁止**
