## 1. 受講者 5 問フロー

**テストする機能** — 受講者が研修コード入力後、名前・所属、5 問、確信度、送信完了まで進めること

**目的** — 研修本番で受講者が迷わず回答を完了できることを確認する

**受け入れ条件** — 気づき → 共有・行動 → 判断基準 → 一言メモを 5 回繰り返し、5 回目の後に確信度と送信確認へ進む

**どのようにテストするか** — 受講者画面を開き、研修コード、名前、所属を入力する。各設問でカードを選び、一言メモを任意入力して `next` で最後まで進む。5 問目の後に確信度を選び、送信する

**コード上の期待値** — 送信データの `rounds.length` が `5`。`participantName` / `affiliation` は trim 済み。`confidenceLevel` は `1`〜`5`。`roomId` が入室済み room の ID になる

**成功条件** — 途中で詰まらず送信完了画面まで到達する。必須項目未入力時は分かる文言で止まる

## 2. 研修コード入室

**テストする機能** — 受講者の研修コード入力

**目的** — 研修対象者だけが名前・所属入力へ進めることを確認する

**受け入れ条件** — 正しい研修コードでは名前・所属欄が表示される。不正コードでは名前・所属欄を出さない

**どのようにテストするか** — まず不正なコードを入力してエラーを確認する。次に正しい研修コードを入力し、名前・所属欄が出ることを確認する

**コード上の期待値** — 正しいコードでは `verifyTrainingCode()` が `{ ok: true, roomId }` を返す。不正コードでは `{ ok: false, message: "正しい研修コードを入力してください" }` を返す。`canShowProfileFields(roomId)` は `true`

**成功条件** — 不正コード時に「正しい研修コードを入力してください」と表示される

## 3. 管理者コード入室

**テストする機能** — 管理者画面の入室ロック

**目的** — 管理者以外が設定・回答一覧を見られないことを確認する

**受け入れ条件** — 管理者コード未入力または不正時は管理 UI を表示しない。正しいコードで管理 UI を表示する

**どのようにテストするか** — 管理者画面を開き、未入力・不正コードで入室できないことを確認する。次に正しい管理者コードを入力し、管理 UI が表示されることを確認する

**コード上の期待値** — 正しいコードでは `verifyAdminCode(input, expected)` が `true`。不正コード・空文字では `false`。入室後は `isAdminSessionActive()` が `true`

**成功条件** — 管理者コードなしでシーン編集・研修コード設定・回答一覧に入れない

## 4. iframe レイアウト

**テストする機能** — 受講者 iframe と管理者 iframe の表示

**目的** — 3DVista への埋め込み時に、狭い表示領域でも研修が進められることを確認する

**受け入れ条件** — 受講者は 25% 帯、管理者は 40% 帯相当の枠で主要操作が見える

**どのようにテストするか** — 受講者・管理者それぞれの埋め込み確認画面を開く。ブラウザ幅・高さを変え、主要画面を一通り表示する

**コード上の期待値** — アプリ本体は iframe 内で `width: 100%` / `height: 100%` 相当で表示される。受講者アプリ CSS に固定の `25vh` 前提を持たない

**成功条件** — 文字・カード・ボタンが枠外にはみ出さない。受講者側は帯内スクロールバーなしで進められる

## 5. 回答の保存・表示

**テストする機能** — 受講者の送信結果を管理者が確認する流れ

**目的** — 研修後に講師・管理者が回答を確認できることを保証する

**受け入れ条件** — 受講者が送信した回答が、管理者画面の回答一覧・詳細に表示される

**どのようにテストするか** — 受講者画面で 1 件送信する。管理者画面に入り、回答一覧を開いて該当回答を選択する

**コード上の期待値** — `appendResponse(submission)` 後、`loadResponses()[0].id` が送信した `submission.id` と一致する。詳細表示では `sceneId` に対応するシーンが解決できる

**成功条件** — 名前、所属、回答内容、確信度、送信日時が確認できる

**補足** — 現在の localStorage 版では 5173 / 5174 が別オリジンのため本番同等の共有確認はできない。本番確認は Sheet API 実装後に行う

## 6. client / room 分離

**テストする機能** — 複数クライアント・複数研修回のデータ分離

**目的** — 他社や別研修回の回答が見えないことを確認する

**受け入れ条件** — `clientId` が違うデータ、または `roomId` が違うデータは回答一覧に混ざらない

**どのようにテストするか** — client A / room A に回答を送る。別 client または別 room の管理画面を開き、その回答が表示されないことを確認する。正しい client + room では表示されることも確認する

**コード上の期待値** — `GET responses?client=client-a&room=room-a` は room A の回答だけを返す。`room-b` への GET には room A の `submission.id` が含まれない。不正 `client` / `room` はエラー結果を返す

**成功条件** — 同一 `client` + 同一 `room` の回答だけが見える。不正な `client` / `room` はエラーになり、画面が壊れない

**補足** — Sheet API の GAS・本番切替・画面配線は最小実装済み。Sheet API mock 経由の Playwright は Green。本項目は複数端末・実 GAS / 実シートで本番同等に確認する

## 7. PDF 出力

**テストする機能** — 管理者画面からの回答 PDF ダウンロード

**目的** — 講師・管理者が研修結果をファイルとして保存・共有できることを確認する

**受け入れ条件** — 回答済み 1 件を選択し、PDF をダウンロードできる

**どのようにテストするか** — 管理者画面で回答済み 1 件を開き、PDF ダウンロードを実行する。生成された PDF を開いて内容を目視する

**コード上の期待値** — PDF 生成関数が空でないバイナリを返す。先頭が PDF シグネチャ相当（例: `%PDF`）で、入力した回答 ID・シーン名・5 問分の回答が生成対象に含まれる

**成功条件** — PDF にシーン名、受講者情報、5 問分の回答、確信度が含まれる

**補足** — Phase 3 入口として PDF 生成ロジックの最小実装、開ける最小 PDF 構造、日本語対応・最低限の装飾テスト、管理者画面からのダウンロード UI 代表テストは完了。実 PDF の目視確認は未実施

## 8. 自動テスト

**テストする機能** — shared の純関数・入室ロジック・保存ロジック・API 契約

**目的** — 人間が毎回見なくてもよい細かい仕様を固定する

**受け入れ条件** — `npm test` が Green になる

**どのようにテストするか** — ルートで `npm test` を実行する。失敗した場合は、失敗した `*.test.ts` と対象ロジックを確認して修正する

**コード上の期待値** — `npm test` が exit code `0` で終了する。Vitest の対象は `shared/src/**/*.test.ts`

**成功条件** — 既存テストに加え、Phase ごとの対象テストが増えても CI / ローカルで安定して通る
